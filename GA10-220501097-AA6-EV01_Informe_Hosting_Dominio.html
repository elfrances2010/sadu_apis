Introducción

El proceso de despliegue en producción representa la fase culminante en el ciclo de vida del desarrollo de software. En esta etapa, las aplicaciones desarrolladas e integradas en entornos locales de pruebas son trasladadas a una infraestructura en la nube accesible globalmente mediante protocolos web estándar (HTTP/HTTPS) y nombres de dominio calificados (FQDN).

El presente documento técnico detalla de forma exhaustiva la configuración de servicios de Hosting PaaS (Platform as a Service) y Dominio para la puesta en producción del sistema SADU APIs (Sistema de Administración Documental). Esta solución informática está estructurada bajo una arquitectura empresarial en Java 17 empaquetada como archivo WAR con Servlets, páginas JSP, Maven, y persistencia relacional en MySQL 8.0.

A lo largo del informe se especifican los recursos tecnológicos utilizados, los criterios de selección de la infraestructura, los comandos ejecutados mediante la interfaz de línea de comandos (Railway CLI), la creación de túneles SSH para la importación de esquemas de bases de datos, la emisión automática de certificados de seguridad SSL/TLS de 256 bits, y las pruebas visuales de validación de funcionamiento en internet.

Objetivo de la Evidencia: Desarrollar una guía técnica estructurada con normas de presentación académicas (APA 7) que evidencie el despliegue funcional del proyecto en un servidor en la nube con acceso por dominio personalizado y base de datos relacional activa.

Comparativa de Servicios de Hosting Evaluados

Antes de definir la plataforma final, se evaluaron diversas alternativas de alojamiento en la nube con base en criterios de compatibilidad con Java WAR, persistencia relacional gratuita y facilidad de integración:

  • Railway Cloud (Seleccionado): Ofrece soporte nativo para Maven y Java WAR mediante webapp-runner, integración inmediata con GitHub, aprovisionamiento de MySQL en el mismo entorno, CLI avanzada con túneles SSH y emisión automática de certificados SSL.
  • Render: Buena alternativa para Node.js y Python, pero presenta limitaciones en los planes gratuitos para contenedores Java pesados y reinicios por inactividad.
  • Heroku: Descontinuó sus servicios de capa gratuita permanente, requiriendo tarjetas de crédito obligatorias para pruebas.
  • Vercel / Netlify: Orientados principalmente a aplicaciones Serverless y Frontend estático (Jamstack), no compatibles con aplicaciones monolíticas Java Servlet/JSP tradicionales.

2. Configuración de Servicios de Hosting (25% de la Evaluación)

A continuación se detalla el procedimiento técnico paso a paso ejecutado para la preparación, compilación y despliegue del código fuente en el servidor PaaS de Railway Cloud.

Paso 2.1: Exclusión de Binarios Temporales (.gitignore)

Para asegurar un repositorio limpio e impedir la subida de archivos compilados pesados, se configuró el archivo .gitignore asegurando que la carpeta target/ generada por Maven no sea rastreada por Git:

# Configuración de exclusión en Git (.gitignore)
target/
scratch/

Paso 2.2: Configuración del Contenedor con Procfile

Las aplicaciones Java Web empaquetadas como `.war` requieren un servidor de aplicaciones Servlet (como Apache Tomcat) para su ejecución. En el archivo pom.xml del proyecto se incluyó el plugin webapp-runner de Heroku/Apache Tomcat, el cual descarga el ejecutable webapp-runner.jar durante la fase de empaquetado.

Posteriormente, se creó un archivo de orquestación llamado Procfile en la raíz del proyecto para indicarle a la infraestructura de Railway cómo ejecutar el archivo WAR enlazándolo dinámicamente al puerto asignado por la variable de entorno $PORT:

# Instrucción de arranque en Procfile
web: java $JAVA_OPTS -jar target/webapp-runner.jar --port $PORT target/sadu_apis.war

Paso 2.3: Autodetector de Base de Datos en Java (Conexion.java)

Para lograr interoperabilidad total entre el entorno de desarrollo local (NetBeans/XAMPP en localhost:3306) y el servidor de producción en la nube, se modificó la clase com.sadu.config.Conexion. Esta implementación evalúa dinámicamente si existen variables de entorno globales (DB_URL, MYSQLHOST, MYSQLPORT, etc.) inyectadas por Railway, o si debe conmutar a la configuración por defecto de desarrollo:

package com.sadu.config;

import java.sql.Connection;
import java.sql.DriverManager;

public class Conexion {
    private static final String URL_LOCAL = "jdbc:mysql://localhost:3306/sadu_apis?useSSL=false&serverTimezone=UTC";
    private static final String USER_LOCAL = "root";
    private static final String PASSWORD_LOCAL = "";

    public static Connection getConnection() throws Exception {
        Class.forName("com.mysql.cj.jdbc.Driver");

        String url  = System.getenv("DB_URL");
        String user = System.getenv("DB_USER");
        String pass = System.getenv("DB_PASSWORD");

        if (url == null || url.trim().isEmpty()) {
            String host = System.getenv("MYSQLHOST");
            String port = System.getenv("MYSQLPORT");
            String db   = System.getenv("MYSQLDATABASE");

            if (host != null && !host.trim().isEmpty() && db != null && !db.trim().isEmpty()) {
                url  = "jdbc:mysql://" + host + ":" + (port != null ? port : "3306") + "/" + db + "?useSSL=false&allowPublicKeyRetrieval=true&serverTimezone=UTC";
                user = System.getenv("MYSQLUSER") != null ? System.getenv("MYSQLUSER") : USER_LOCAL;
                pass = System.getenv("MYSQLPASSWORD") != null ? System.getenv("MYSQLPASSWORD") : PASSWORD_LOCAL;
            } else {
                url  = URL_LOCAL;
                user = USER_LOCAL;
                pass = PASSWORD_LOCAL;
            }
        }

        return DriverManager.getConnection(url, user, pass);
    }
}

Paso 2.4: Administración e Inyección de Variables con Railway CLI

Haciendo uso de la herramienta @railway/cli, se autenticó la sesión del desarrollador y se configuraron las variables de entorno de producción en el servicio sadu_apis dentro del proyecto stunning-truth:

# 1. Autenticación interactiva con la CLI de Railway
npx @railway/cli login

# 2. Vinculación del directorio local al proyecto activo
npx @railway/cli link --project stunning-truth

# 3. Inyección masiva de variables de conexión a la base de datos
npx @railway/cli variable set --service sadu_apis \
  "DB_USER=root" \
  "DB_PASSWORD=IsHyCDSDTwwatejEkulUENKjjbCIBZxo" \
  "MYSQLHOST=mysql.railway.internal" \
  "MYSQLPORT=3306" \
  "MYSQLUSER=root" \
  "MYSQLPASSWORD=IsHyCDSDTwwatejEkulUENKjjbCIBZxo" \
  "MYSQLDATABASE=railway" \
  "DB_URL=jdbc:mysql://mysql.railway.internal:3306/railway?useSSL=false&allowPublicKeyRetrieval=true&serverTimezone=UTC"

Paso 2.5: Apertura de Túnel SSH e Importación del Esquema SQL

Debido a que el puerto MySQL (3306) de Railway opera dentro de una red privada virtual de contenedores (mysql.railway.internal), se generó un par de llaves criptográficas SSH (ed25519) registradas en Railway para abrir un túnel seguro local en el puerto 3307. Posteriormente se ejecutó un script de importación masiva en Node.js que procesó el archivo sadu_apis.sql:

# 1. Generación de clave criptográfica SSH
ssh-keygen -t ed25519 -N "" -f "C:\Users\elfra\.ssh\id_ed25519"

# 2. Registro de la clave pública en Railway
npx @railway/cli ssh keys add

# 3. Creación del túnel SSH local al puerto 3307 de la BD remota
npx @railway/cli connect MySQL --tunnel-only -P 3307

# 4. Importación del script SQL mediante cliente Node.js (mysql2)
node scratch/import.js

Resultado de la Importación: Se crearon correctamente las 6 tablas relacionales del sistema (roles, usuarios, documentos, comunicaciones, logs_auditoria, mensajes_chat) junto a sus llaves primarias, foráneas e índices únicos.

Solución a Problemas Comunes durante la Configuración

  • Error "The specified path src/main/webapp does not exist": Ocurrió porque Nixpacks intentó ejecutar por defecto webapp-runner apuntando al código fuente en lugar del archivo WAR. Se solucionó definiendo la ruta explícita target/sadu_apis.war dentro del Procfile.
  • Falla de autenticación MySQL "caching_sha2_password": El cliente binario de MySQL local no contenía la librería DLL adecuada. Se resolvió creando un script automatizado con el driver nativo mysql2 en Node.js a través del túnel SSH.
  • Error "Communications link failure": Se presentó antes de configurar las variables de entorno de la base de datos. Se solucionó inyectando las credenciales internas de la red privada de Railway mediante la CLI.

4. Configuración de Servicios de Dominio (25% de la Evaluación)

La configuración del dominio permite que la aplicación sea accesible a través de una dirección web amigable en lugar de una dirección IP cruda o una URL efímera.

Paso 4.1: Asignación de FQDN y Public Networking

En el panel de control del servicio sadu_apis dentro de Railway, se accedió a la pestaña Settings > Public Networking para generar un subdominio público administrado en la infraestructura de Railway Cloud:

# Dominio Calificado (FQDN) Asignado
https://saduapis-production.up.railway.app

# Binding del Puerto de la Aplicación
Target Port: 8080 (Mapeado internamente hacia el servidor Tomcat Webapp Runner)

Paso 4.2: Configuración de Certificados de Seguridad SSL/TLS (HTTPS)

Railway aprovisiona de forma automática un certificado de seguridad digital emitido por la autoridad certficadora Let's Encrypt. Esto garantiza la encriptación de extremo a extremo (TLS 1.3) para todas las peticiones HTTP que transitan hacia los formularios de autenticación del sistema SADU.

Paso 4.3: Mantenimiento y Verificación del Dominio

Para asegurar la continuidad del servicio, Railway implementa verificaciones de estado (Health Checks) mediante peticiones HTTP periódicas. En caso de fallas en el contenedor, el sistema realiza reinicios automáticos y reasigna el tráfico sin interrupción del dominio.
